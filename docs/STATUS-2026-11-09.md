## 3. 透明玻璃（A+C）为什么没做成

用户要的是上游那种状态：**图标整体半透明玻璃、透出紫蓝壁纸；Dock / 搜索按钮 /
widget 也半透明**。三轮真机证明这不是注入层写法问题，而是**驱动层 alpha 合成**：

- v89：CGImage 逐像素 alpha 被 QuartzCore 反预乘丢弃（白色图标内部 `(235,235,235)` 逐字节不变）；
  但圆角外的透明像素**确实透出了壁纸** → alpha 通道本身是通的。
- v89：`SBDockView` 的 group opacity 让整个 Dock 连 4 个图标一起消失。
- v91：`CALayer.opacity < 1` 让 PNG fallback 图标全部消失；原生渲染的时钟却正常变玻璃。
- 结论：**在当前驱动上模拟透明度走不通**，必须修驱动层 alpha 合成，并逐步让原生图标路径接管。

## 4. 最新未解问题：点图标闪红 + 启动动画掉帧

用户反馈（图标样式满意，只要修这个）：**打开任意图标出现红色一瞬间，然后动画掉帧卡顿**。

### 已取到的证据（19:05 实时内核日志 + 连拍）

- 帧时间线：tap 后帧空窗 **50,235 / 52,381 / 98,955 / 108,727 us**；
  稳定帧间隔约 **50 ms（≈20 fps）**；median 17.2 ms、p90 50.9 ms、p99 141 ms，
  `>100 ms` 20 次、`>200 ms` 12 次。
- `com.apple.iconservices` 同步调用反复约 **300 ms**（30 次 `TIMEOUT`，即 v82 加的冷超时），
  日志里 `us=301056` / `369121` / `382274` 等一串；`DEADCACHE` 共 662 次，
  集中在 `managedconfiguration.profiled`、`biome.access`、`coremedia.*` 等死服务。
- `sb26: icons +Ns: filled=23 refilled=23` —— 定时刷新每轮把 23 个图标全部重填，
  可能是周期性 CPU 峰值与 iconservices 请求风暴的来源，值得先查。
- 红色**日志里没有任何记录**，是毫秒级渲染瞬态。`oem screenshot` + `get_staged`
  单次 **0.43 s**（14 MB 全屏），连拍 12 帧只看到 0.5 s 时还是主屏、1.0 s 已变黑，
  红色被漏掉；`tap-burst.py` 的红像素统计全程 0%。
- 帧缓冲物理地址日志里有：`MiniIOMobileFramebuffer: ... the boot framebuffer at 0xfc800000`。

### 建议的下一步（按性价比）

1. **高频采样定位红色**：用 `oem stage <ADDR> <HEXLEN>` 只读 framebuffer 一行
   （`0xfc800000 + y*5120`，长度 `0x1400` 裸十六进制），每次几千字节，
   可在 tap 后做到几十毫秒一次采样，画出红像素占比随时间曲线，
   判断红色是全屏清屏色、launch image 占位、还是图标放大动画的中间帧。
   注意 `oem stage` 的 ADDR / LEN **都是裸十六进制**。
2. **先砍定时图标刷新**：`sb26_fill_all_icons` 的 `refilled=23` 每轮全量重填，
   改成只在 bundle / 图标内容真变化时更新，观察 p90 / tap 后空窗是否下降。
3. **缩短 iconservices 冷超时**：现在 300 ms 是 v70 定的（防止 SpringBoard 被 4 s 等待打死）。
   可以在缓存命中率高的前提下分档：冷 key 降到 60–100 ms，热 key 继续即时返回，
   但必须保证永远返回可解码的 dictionary（NULL 会 abort SpringBoard）。
4. **帧率本身**：`fb_hz=120 fb_ca_hz=120` 已经在 cmdline，实测仍 20 fps，
   查 `fb_threads=2 fb_flip=2` 与 backboardd 合成耗时，别只盯着 XPC。

## 5. 启动与取证流程（复现用）

```sh
# 绝不 flash。设备若停在 loader，先 oem stop -> reboot bootloader，
# 通常会先回 Android，脚本会自动 adb reboot bootloader。
OUTDIR=$PWD/once-vXX OBSERVE=150 SHOTS="70 105 135" \
  bash warsaw-port/tools/boot-once-v2.sh \
    Mu-warsaw-xnu-k10.img payload-vXX.bin
# 系统盘默认 F:/warsaw-ios26/tree/userland/system26.apfs（v84 的 38-job 版）
```

- 重新构建小根盘：`MSYS=winsymlinks:nativestrict PREBUILT=1 IOS=../ios26 RC=rc.metal bash build.sh`
- arm64e 注入库 / 驱动走 CI `build-host-tools.yml` 的 `arm64e-userland` job，
  从 `arm64e-progs` artifact 取 `libredwood-sb26.dylib` / `libredwoodmetal.dylib` / `RedwoodMetal`。
  多个并发 run 抢推 `metal-artifacts` 分支会让 job 标 failure，但**编译本身成功、artifact 正常**。
- 载荷生成脚本 `mkpayload-vNN.py`（本地，含本地路径故不上传）基于 v86 基线只替换 `root26.apfs`。
- 触摸注入：`oem sh "/redwood/bin/rwtouch tap 0.13 0.375"`、
  `oem sh "/redwood/bin/rwtouch swipe 0.5 0.99 0.5 0.4 250"`。
- 连拍工具 `docs/tools/tap-burst.py`（已上传）。

## 8. 硬边界（接手请遵守）

- **只用 `fastboot boot`，绝不 `flash`**。
- Apple 私有文件、IPSW、厂商固件、`system26.apfs`、payload 二进制只留本地，不上云、不进 Git。
- 公开仓库只放开源源码、补丁、脚本、文档与截图。
